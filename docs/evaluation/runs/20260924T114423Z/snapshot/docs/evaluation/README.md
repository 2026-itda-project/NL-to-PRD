# Requirement Extraction / Gap Analysis 평가

자연어 요구사항 분석 모듈의 품질을 측정하고, 변경 전후 결과와 개선 근거를 기록하기 위한 평가 자료다.

**정답 및 실행 정책 v1.0: 사용자 승인으로 고정. 실행 결과와 의미 채점 상태는 각 실행 보고서에서 관리한다.**

## 평가 범위

평가 대상은 다음 흐름이다.

```text
자연어 입력 → Requirement Extraction / Structuring → Gap Analysis → Handoff JSON
```

명시된 요구사항의 보존, 미언급 내용의 과잉 확정, 핵심 누락, 모호성 탐지, Blocking 판단, 구조화 결과의 일관성을 확인한다. Clarification 답변 반영 및 최종 PRD 품질은 이후 통합 평가에서 다룬다.

[SnowChat 연결 검증](../snowchat-verification.md)은 실제 Gateway 및 UI 실행 기록이다. 해당 기록을 이번 품질 평가 점수로 사용하지 않는다.

평가 자료는 `evaluation/m1` 브랜치에서 관리할 예정이다. 현재 브랜치 생성과 게시 전이다. 코드 개선은 최신 `main`에서 별도 브랜치로 진행하고, 평가 시에는 대상 코드 커밋과 평가 자료 버전을 함께 기록한다. 실행기는 `run_evaluation.py`이며 원본 응답과 실행 보고서는 `runs/`에 보존한다.

## 실행 절차

1. 시나리오의 필수 사실, Gap 필요성, Blocking 및 충분한 입력의 완료 범위를 검토한다.
2. 시나리오 문서의 분모 표와 묶음 채점 기준, 아래 재시도 정책을 검토한다. 12개 사례의 승인 여부를 검토 표에 기록하고 모두 승인된 뒤 정답 v1.0을 고정한다. 문서 수정만으로 승인 또는 실행을 대신하지 않는다.
3. 코드, Prompt, Schema, 모델 설정을 고정하고 각 시나리오의 반복 슬롯 3개를 실행 전에 배정한다. 계획 규모는 12개 입력 × 3슬롯 = 36슬롯이며, 재시도 없이 모두 성공하면 72회 Stage 호출이다.
4. Schema와 참조 관계를 검사하고, 의미상 정확성은 사람이 채점한다. AI 보조 판정은 검토 후 확정한다.
5. 오류별 원인 가설과 변경 내용을 기록하고 같은 조건으로 재평가한다. 개선과 회귀를 함께 보고한다.

평가 사례에서 전달하는 내용은 입력 본문으로 제한한다. 기존 Stage별 시스템 Prompt와 Schema는 유지한다. Extraction은 원문과 파이프라인 메타데이터를 받고, Gap 단계는 원문과 실제 Extraction 결과를 받는다. 정답, 평가 메모, 시나리오 제목은 어떤 Stage에도 전달하지 않는다. v1.0의 12개 사례와 분모는 승인된 기준으로 사용한다.

### 반복 슬롯과 재시도

- 슬롯은 `시나리오 ID + 반복 번호(1~3)`로 식별한다. 최초 시도와 재시도에는 별도 attempt 번호를 부여한다.
- `timeout`, `rate_limit`, `gateway_error`만 슬롯당 최대 2번 재시도한다. 최초 시도를 포함해 최대 3회이며 매번 분석 전체를 다시 호출한다.
- 첫 재시도 전 5초, 두 번째 전 15초 대기한다. 평가 실행기가 응답에서 유효한 `Retry-After`를 확인할 수 있으면 해당 값을 우선한다. 값이 없거나 유효하지 않으면 위 고정 대기를 적용한다. 이 값을 얻기 위해 파이프라인을 변경하지 않는다.
- `structured_output_invalid`은 재시도하지 않는다. Blocking Gap 연결 누락, Schema 오류, 잘못된 ID 등 품질 실패를 재호출로 교체하지 않는다.
- `missing_api_key`, `authentication_failed`, `model_unavailable`, `invalid_config`는 재시도하지 않고 평가 실행 전체를 중단한다. 설정 수정 후 새로운 평가 실행 ID로 36슬롯을 처음부터 시작한다.
- 중단된 실행의 응답과 오류는 삭제하지 않고 '설정 오류로 중단'으로 보존한다. 아직 실행하지 않은 슬롯은 미실행으로 표시한다. 중단 실행과 새 실행의 점수는 합산하지 않는다.
- 위 목록에 없는 오류는 재시도하지 않는다. Provider 내부 자동 재시도가 있다면 이를 포함한 호출 이력을 실행 전에 확인하며, 슬롯 재시도와 별도 표기한다.
- 전체 분석 재시도로 다시 수행된 Requirement Extraction과 Gap Analysis 모두 사용량 집계 대상이다. 각 시도의 응답에서 확인 가능한 값만 합산하고, 없는 값은 N/A로 둔다. 실패 응답에는 이미 실행된 Stage의 Usage도 없을 수 있으므로 0으로 대체하거나 추정하지 않는다. 보고서에는 확인 가능한 Token 합계, Usage 미확인 시도 수를 함께 표시하며, 누락이 있으면 전체 소비량은 산출 불가로 표기한다.
- 재시도는 같은 슬롯에 속한다. 성공한 결과 3개를 채우기 위해 슬롯을 추가하거나 실패 슬롯을 교체하지 않는다.
- 슬롯의 마지막 시도가 실패하면 최종 실패로 남긴다. 의미 채점에는 성공한 슬롯의 최종 응답만 사용하며, 이전 실패 시도와 사용량은 보존한다.
- 최초 시도 성공률, 최종 슬롯 성공률, 재시도 횟수, 전체 시도 성공률을 구분한다. 재시도로 복구된 성공을 최초 성공으로 기록하지 않는다.

현재 Provider에는 내부 자동 재시도가 없고 Retry-After를 API 응답으로 전달하지 않는다. 따라서 현재 실행에는 5초, 15초 고정 대기가 적용된다. 실행기는 순차 호출하며 HTTP 자체 연결 오류나 Timeout을 API의 timeout 코드로 바꾸지 않는다. 서버 완료 여부가 불명확한 실행기 오류는 자동 재시도 없이 실행을 중단하고 별도 실행 상태로 남긴다.

## 정답 및 채점 규칙

정답은 특정 문장이나 출력 ID의 일치를 요구하지 않는다. 입력에서 확인되는 사실과 서비스 동작을 결정하는 데 필요한 정보를 의미 단위로 비교한다.

| 표기 | 의미 |
| --- | --- |
| R | 입력에 직접 명시된 필수 사실 |
| G | 핵심 누락, 모호성에 대한 필수 Gap. 검토 승인 전에는 초안 판단 |
| A | 발견 여부를 필수 점수에 넣지 않는 허용 Gap. 예시는 전체 허용 목록이 아님 |
| F | 미언급 내용의 확정, 확정된 내용의 미정 처리 등 금지 결과 |
| C | `confirmed`, `source=initial_input`, `Requirement.blocking=false` |
| N/B | `needs_clarification`, `source=initial_input`, `Requirement.blocking=true` |
| N/N | `needs_clarification`, `source=initial_input`, `Requirement.blocking=false` |

### 사실과 상태

- 하나의 Requirement에 여러 사실이 정확히 담기면 각 사실을 인정한다. 같은 사실의 반복은 중복 점수를 주지 않는다.
- 사실과 추정이 섞인 항목은 사실 회수와 과잉 확정을 각각 기록한다.
- 확정 사실과 미정 사실을 한 Requirement에 섞으면 각 의미 단위에 출력의 상태를 적용한다. 사실이 보존돼도 확정 사실을 `needs_clarification`으로 내렸다면 해당 단위의 상태는 오답이다.
- 현재 ExtractionOutput의 InitialRequirement는 proposed와 initial_input 이외의 source를 Schema에서 거절한다. 해당 위반은 성공 응답에서 의미 채점할 수 없으며 응답 메시지만으로 실패 원인을 세분화할 수 없다. 성공 응답에서 위반 0건이라는 결과를 모델 품질 근거로 사용하지 않는다.
- `acceptance_criteria`도 입력에 근거가 있는지 의미 단위로 검사하고, 근거 없는 추가 조건의 개수와 해당 슬롯 비율을 보고한다. 입력 사실을 관찰 가능한 완료 조건으로 재서술한 것과 새로운 정책을 추가한 것을 구분한다.
- 명시된 행위자로부터 역할 존재는 인정하되, 입력에 없는 권한을 추가하면 오류다.
- 관련 내용이 언급됐지만 미정, 모호하면 `needs_clarification`으로 평가한다. 관련 내용 자체가 없으면 Requirement가 아닌 Gap으로 표현해야 한다.
- 분모는 시나리오 문서의 회수율 분모 표를 따른다. L02 R5 등 지정 항목은 분해했고 나머지는 명시된 묶음으로 채점한다. 묶음은 모든 구성 조건이 충족돼야 1점이며 부분 점수는 없다. 시작일, 종료일, 사유 같은 입력 구성 필드는 분리하지 않는다. 실행 결과를 본 뒤 단위와 분모를 변경하지 않는다.

### 채점 근거와 판정 위치

필수 사실은 requirements의 description 및 acceptance_criteria에서 확인하며 해당 Requirement의 상태를 적용한다. AC에만 있으면 위치를 기록한다. Gap에만 있는 사실, ID나 category만으로는 추출 회수를 인정하지 않는다.

| 슬롯 | 정답 ID | 대응 출력 ID 및 필드 | 판정 | 원문 근거 |
| --- | --- | --- | --- | --- |
| 사례-반복 | R 또는 G ID | REQ/GAP ID, description/acceptance_criteria | 회수/누락, 상태, Blocking | 판단에 사용한 출력 인용 |

새로운 허용 Gap에는 판단 근거를 남기고 동일 결정에는 동일 판정을 적용한다. 판정이 바뀌면 해당 결정이 있는 모든 응답을 재검토한다. 정답 변경이 필요하면 새 버전으로 기록하며 이전 결과에 유리한 일부 변경만 적용하지 않는다.

### Gap과 Blocking

- 출력 Gap과 정답을 각각 결정 단위로 분해해 대응한다. 한 출력 Gap이 저장소 제품과 인증 방식을 모두 지적하면 두 정답 단위의 회수를 인정한다.
- 정답 단위당 회수 점수는 최대 한 번이다. 동일 결정이 여러 출력에 반복되면 추가 점수를 주지 않고, 첫 출현을 제외한 반복 단위 수를 별도 집계한다.
- 매칭된 동일 결정의 Blocking이 출력마다 다르면 해당 정답 단위의 Blocking 판정은 불일치로 처리한다. 기대값에 맞는 출력만 골라 채점하지 않는다.
- 대응되지 않은 출력은 허용 Gap, 불필요 Gap으로 판정한다. 허용 목록은 예시이므로 새 결정도 범위와 필요성에 따라 근거를 기록한다. 매칭 실패만으로 불필요하다고 판정하지 않는다.
- 유용한 누락과 불필요한 기능 제안이 섞이면 각각 채점한다. 반복 자체는 중복 지표로 기록하며, 내용이 불필요한 경우에만 불필요 Gap에도 포함한다.
- 선택지로 든 예시와 특정 정책을 필수라고 단정한 결과를 구분한다.
- `Gap.blocking`은 핵심 누락, 모호성의 확인 필요성, `Requirement.blocking`은 기존 미결정 Requirement의 진행 차단 여부로 평가한다.
- `clarification_needed`는 `any(gap.blocking)`과 같아야 한다.
- Category 경계에서 의미가 맞는 대체 분류는 허용한다. 범위를 왜곡하는 분류는 근거와 함께 오류로 기록한다.
- 참조 검사는 ID 존재, 관련 Requirement 연결 누락, 무관한 Requirement 연결을 각각 기록한다. 유효한 ID라도 의미적으로 무관하면 연결 오류다.
- 관계는 실제 출력 ID로 검사한다. R/G 번호는 채점용이며, 관련 Requirement가 없는 서비스 전반의 Gap은 빈 참조 목록을 허용한다.
- 사례의 관련 R 표시는 관계 검사 기준이며 Gap 의미 회수의 조건이 아니다. 추출에서 Requirement를 누락해 연결할 ID가 없어도 성공 응답의 Gap이 결정 사항을 맞히면 회수는 인정한다. 추출 누락과 참조 대상 부재를 별도 기록한다. 관련 Requirement가 존재하는데 연결하지 않은 오류와 구분한다.
- 분석 전체가 계약 실패로 종료된 경우에는 중간 결과를 추정해 위 의미 점수를 부여하지 않는다.

## 평가 지표

| 지표 | 계산 및 기록 방식 |
| --- | --- |
| API/계약 성공률 | 최초 성공 슬롯 / 전체 슬롯, 최종 성공 슬롯 / 전체 슬롯, 성공 시도 / 전체 시도를 각각 표시 |
| 명시 사실 회수율 | 회수한 필수 R 의미 단위 / 전체 필수 R 단위 |
| 상태 정확도 | 기대 상태와 Requirement.blocking이 모두 맞는 R / 회수한 R |
| 잘못 확정한 내용 | 입력에 근거가 없거나 충돌 중인데 확정한 의미 단위 수 및 해당 실행 비율 |
| 핵심 Gap 회수율 | 회수한 필수 G 의미 단위 / 전체 필수 G 단위 |
| Gap Blocking 정확도 | 기대 Blocking이 맞는 매칭 G / 매칭된 필수 G |
| 불필요한 Gap | 무관, 이미 해결됨, 범위 밖 결정 단위 개수 및 전체 출력 결정 단위 대비 비율. 분모는 중복을 제거한 고유 출력 결정 단위 수 |
| 중복 Gap | 동일 결정의 첫 출현을 제외한 반복 단위 수 |
| 근거 없는 AC | 입력에 없는 추가 조건의 의미 단위 수 및 해당 오류가 있는 성공 슬롯 비율. 상태/출처 제한은 Schema 보장 항목으로 별도 표기 |
| 불필요한 차단 | 충분한 입력에서 잘못 생성된 Blocking Gap 수 |
| 인계 일관성 | ID 고유성, 참조 존재, Blocking Requirement와 Gap 연결, clarification_needed 일치 |
| 사용량 및 시간 | Stage별 실제 Token Usage, 경과 시간, 전체 요청 시간 |
| 반복 안정성 | 고정 3슬롯의 성공/실패 패턴과 성공 슬롯에서의 사실, Gap 탐지 및 상태, Blocking 변동. 채점 가능 슬롯 수 병기 |

### 집계와 해석

의미 지표 표에는 **성공한 슬롯의 최종 응답 기준**이라는 제목과 대상 슬롯 수를 표시한다. 상태 정확도는 명시 사실 회수율과, Gap Blocking 정확도는 핵심 Gap 회수율과 같은 표에 둔다. 어려운 항목을 누락하면 조건부 정확도가 높아질 수 있으므로 정확도만 단독 보고하지 않는다.

분모가 0이면 N/A로 표시한다. 필수 Gap이 없는 입력은 회수율 대신 잘못 생성된 Gap과 차단을 확인한다. 실패, 빈 답변, 정상적으로 요구사항이 없는 결과를 구분한다. 실패 슬롯의 의미 점수는 0점이나 정답으로 대체하지 않고 채점 불가로 남긴다.

- 각 시나리오에서 성공 슬롯별 지표를 계산한 뒤 평균을 내고, 성공 슬롯 수/3과 함께 표시한다.
- 주요 요약은 L04를 제외한 11개 시나리오의 동일 가중 매크로 평균이다. 지표별 N/A 시나리오는 제외하고 포함 수와 제외 사유를 표시한다. 전부 실패한 시나리오를 제외했다면 생존한 시나리오만의 조건부 평균임을 명시한다.
- L04는 L01과의 표현 안정성 비교로 별도 보고한다. 둘을 포함한 12개 평균을 대표 점수로 쓰지 않는다.
- 의미 단위 합산(마이크로)은 보조 결과다. 긴 명세가 더 큰 비중을 차지하므로 매크로와 구분한다. 휴가/비휴가 결과도 나누어 표본 구성의 편향을 드러낸다.
- 36슬롯은 12종 입력의 반복이다. 일반 Web SaaS 전체 정확도, 통계적 유의성, 입력 길이의 인과 효과를 주장하지 않는다. 합격선이나 가중 종합점수는 두지 않는다.

### 계약 실패와 관측 한계

현재 `pipeline.py`는 Blocking Requirement를 참조하는 Blocking Gap이 없으면 `structured_output_invalid`로 분석 전체를 거절한다. L03, L06, E01, A01, D01 등에서 올바르게 추출한 미정 Requirement의 Gap 누락이 계약 실패로 바뀔 수 있다. 반대로 미정을 confirmed로 잘못 추출하면 같은 검사가 적용되지 않을 수 있다.

의미 점수 옆에 아래 오류의 시도 수와 최종 실패 슬롯 수를 함께 표시한다.

이번 평가의 오류 분류는 API 응답의 오류 코드와 메시지만 사용한다. 서버 로그나 중간 Stage 결과를 근거로 세부 분류하지 않는다.

| 오류 유형 | 응답 기준 |
| --- | --- |
| Gateway/Provider | 응답의 인증, 모델, Rate Limit, Timeout 등 오류 코드별로 집계 |
| Blocking Gap 연결 누락 | `미결정 핵심 요구사항에 연결된 Blocking Gap이 누락됐습니다`와 일치하는 메시지만 해당 |
| JSON/Schema 구분 불가 | `LLM 결과가 출력 Schema를 충족하지 않습니다`는 두 오류가 같은 문장이므로 분리하지 않음 |
| 기타/세부 원인 미확인 | ID, 내용, 관계 검증의 통합 메시지 또는 위 기준으로 구분되지 않는 오류 |

비교 시 앞뒤 공백과 문장 끝 마침표만 제거한다. 부분 문자열이나 공통 `structured_output_invalid` 코드만으로 Blocking Gap 연결 누락을 추정하지 않는다. 원본 메시지는 함께 보존한다. 존재하지 않는 ID와 중복 ID도 통합 메시지만으로 분리하지 않는다. `json_invalid` 통계를 얻기 위해 로그를 조회하거나 파이프라인을 수정하지 않는다.

Blocking Gap 연결 누락은 품질 문제가 하드 에러로 처리된 경우다. 세부 원인 미확인 건수와 함께 별도 집계한다.

`analyze()` 실패 시 파싱된 Stage 결과는 반환값이나 `AnalysisError`에 남지 않는다. 이번 평가는 파이프라인을 변경하지 않으며, 실패 응답을 감싸는 실행기만으로 중간 결과를 채점하지 않는다. 해당 슬롯은 의미 채점에서 제외됐음을 명시한다. 성공률과 오류 표를 함께 제시해도 성공 사례만의 의미 점수라는 한계가 사라지는 것은 아니다. 실패 전 결과 보존이 필요하면 별도 변경과 평가 버전으로 관리한다.

### 사례 구성의 한계와 짝 비교

수정/취소의 누락은 L01, R01, E01, A01에서 허용 Gap이며 L06의 충돌은 필수다. AGENTS.md의 8개 영역은 우선 확인 영역으로, 모든 입력에서 필수 Gap을 요구하는 목록은 아니다. 이번 세트만으로 수정/취소 누락 탐지 능력을 충분히 평가할 수 없으며, 타당한 허용 Gap을 감점하지 않는다.

L02, L05, R02는 긴 명세와 명시적 제외 범위를 포함한다. 긴 입력에서도 핵심 미정/충돌이 있는 L03, L06과 비핵심 미정만 있는 S01의 차단 결과를 별도 표시한다. 길이만으로 질문 여부를 나누는 경향을 점검하되 인과관계로 해석하지 않는다.

S01/E01은 같은 미정 표현에 대한 판단을 비교한다. S01 배지 색상은 N/N 및 `clarification_needed=false`, E01 기준 금액은 N/B와 해당 Blocking Gap을 기대한다. E01에는 다른 필수 Gap도 있으므로 `clarification_needed=true`만으로 기준 금액 처리가 맞았다고 판단하지 않는다.

### 개선 전후 비교 범위

전체 슬롯 성공률, 각 버전의 조건부 의미 점수, 양쪽에서 채점 가능한 시나리오의 비교, 새로 성공/실패한 사례를 함께 보고한다. 성공 대상이 달라진 평균만으로 개선을 주장하지 않는다.

이번 실험은 실제 추출 결과를 사용하는 전체 분석 파이프라인 평가다. Gap 모델 단독 성능으로 해석하지 않는다. 빈 입력, 긴 입력 한계, 입력 내 지시문 등 견고성은 이 12개 의미 평가의 검증 범위가 아니다.

## 재현 정보 및 보고서

실행마다 다음을 보존한다.

- 평가 실행 ID, 시나리오 ID, 정답 버전, 슬롯 ID, attempt 번호, run_id, 최초/재시도 여부 및 재시도 사유
- 실행 상태(완료/설정 오류로 중단), 미실행 슬롯, 재시도 대기 시간 및 Retry-After 적용 여부
- 원본 입력 및 응답, 오류 및 재시도 기록
- 코드 커밋, 평가 자료 커밋, Prompt, Schema 버전 또는 파일 해시
- 미커밋 변경이 있다면 변경 내용 및 파일 해시
- Provider, 실제 모델 ID, 명시 또는 기본 Reasoning 설정
- 시작, 종료 시각, 경과 시간, 실제 Usage

미제공 값은 N/A로 기록한다. 신뢰 가능한 비용 정보가 없으면 Token Usage까지만 기록한다. API Key, 인증 Header, `.env` 원문은 저장하지 않는다.

보고서는 아래 순서로 작성한다.

1. **목적과 범위:** 평가 대상과 제외 범위
2. **구현 및 실험 조건:** Stage, Provider 구조, 코드, Prompt, Schema, 모델 버전
3. **평가 방법:** 정답 검토 이력, 표본 수, 반복 횟수, 채점 및 제외 기준
4. **관측 결과:** 지표, 정상, 오류 사례, 원본 응답 근거
5. **개선 이력:** 관측 → 원인 가설 → 변경 → 동일 조건 재평가 → 회귀 여부
6. **한계와 후속 검증:** 미해결 문제, 개선 기대, 검증 시점

올바르게 남긴 미결정 Gap은 분석 실패로 보지 않는다. 과잉 확정과 필수 Gap 누락은 현재 모듈의 개선 대상으로 기록한다. 후속 Clarification, Review가 해결할 것으로 예상하는 내용은 검증된 실적과 구분해 가설로 작성한다.

## 실행 방법

저장소 루트에서 실행한다. 환경 변수 또는 로컬 `.env`의 API Key를 사용하며 Secret은 산출물에 기록하지 않는다.

```bash
backend/.venv/bin/python docs/evaluation/run_evaluation.py --self-test
backend/.venv/bin/python docs/evaluation/run_evaluation.py --run
```

실행기는 현재 코드로 별도 로컬 FastAPI 서버를 실행하고 순차적으로 36슬롯을 호출한다. 모델은 두 Stage 모두 gpt-5.6-luna, Reasoning은 기본값으로 고정한다. 최초 모델 조회 실패 시 제공자의 기존 오류 처리로 기록하며 임의 모델 대체는 없다. 실행 순서는 문서의 사례 순서로 12개를 한 번씩 호출하는 것을 3회 반복한다.

실행 전 코드와 문서 해시 및 사본을 고정한다. 원본 응답으로 자동 계약 점검과 사용량만 집계하며 의미 점수는 사람이 근거표를 검토한 뒤 확정한다. 실행 완료는 의미 채점 완료를 뜻하지 않는다.
